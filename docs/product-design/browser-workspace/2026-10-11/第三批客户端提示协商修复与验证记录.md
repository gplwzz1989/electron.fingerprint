# 第三批：用户代理客户端提示协商修复

日期：2026-10-11。对应[技术方案](主流指纹浏览器技术分析与指纹强化防关联开发计划.md)，承接[第二批记录](第二批实施与验证记录.md)。

## 问题与修改范围

第二批六组 HTTPS 样本均未在声明 `Accept-CH` 后发送高熵用户代理提示。当前 Electron 的会话入口返回空委托，Chromium 无法通过所属 Session 的入口完成协商缓存与导航提交。

本次仅修改 `shell/browser/electron_browser_context.cc`，在既有 `GetClientHintsControllerDelegate()` 接口中增加私有实现。配置解析、会话所有权和元数据调整继续复用现有 `FingerprintContext` 与 `ApplyClientHintsOverride`，没有新增配置源、公共头、协议字段或 GN 目标。

- 仅指纹配置及 `modules.clientHints` 开启时接入；无配置、配置关闭和模块关闭保留原有行为。
- 每个 Session 保存独立的协商状态，按完整来源区分；可信主框架来源可保存，子框架权限与委派继续由 Chromium 判断。
- 元数据使用现有校验后的配置快照；配置版本变化时清除旧协商。
- 空协商列表删除对应来源的状态；缓存最多 256 个来源，超限淘汰后重新协商。
- 只允许用户代理提示，不借本次接入开放硬件、屏幕和网络提示；没有手工注入请求头。
- 缓存保存在会话内存，随 BrowserContext 生命周期释放；不写入环境文件，不跨进程保存。

现有 Chromium 内存委托属于未进入当前 Electron 构建图的独立目标。为保持本次 `.cc` 与既有 GN 目标范围，复用已有公开委托协议和标准提示数据结构，在所属会话入口提供私有适配；没有为复用该目标改动构建图或配置。

## 验收入口

新增 `npm run test:fingerprint -- --require-client-hints`，将开启配置环境的高熵请求头缺失设为验收失败；普通诊断仍可采集旧运行时，并在 `gaps` 中保留其缺口。基线记录严格模式标识、本次 `.cc` 哈希及实际运行时哈希。

除已有存储、指纹读回、证书信任、代理路径与故障验证外，新增以下边界对照：

| 场景 | 预期 |
| --- | --- |
| 新来源没有接受提示 | 不提前发送高熵用户代理请求头 |
| 开启配置且站点接受提示 | 页面后续请求包含协商字段，并与页面/独立工作线程元数据一致 |
| 空 `Accept-CH` 响应 | 清除该来源的协商状态 |
| 同会话其他来源 | 不受上述清除影响 |
| 新建独立会话 | 不复用已有会话的协商 |
| 同会话新页面 | 可复用本来源既有协商 |
| 指纹配置或客户端提示模块关闭 | 保留原有行为，不启用本次高熵协商 |
| 脚本关闭 | 即使来源已协商，也不发送高熵提示 |
| 未授权跨来源子框架 | 不继承主框架的高熵提示权限 |
| 服务器请求硬件/网络提示 | 不因本次用户代理接入而启用 |

独立、共享和后台工作线程的源站请求头分别保存。字段已发送时检查其与页面元数据的关系；没有完成高熵协商的线程单独记为未验证，不能以网页协商通过代替后台传输验证。

本轮九个线程请求样本均没有用户代理客户端提示请求头，包括无配置的三个对照；两个开启配置环境的六条缺失记录已单独保留。只读检查发现，Blink 的 `FrameFetchContext` 有请求提示补充入口，`WorkerFetchContext` 没有对应实现。后续先核验上游规范和原生行为，再决定是否需要适配；不把这一观察直接认定为本次会话入口回归，也不为追求字段齐全而无条件注入请求头。
