# 栖界指纹浏览器：SaaS 上线售卖现状分析与开发计划

日期：2026-10-24。依据当前仓库源码与本次只读核查制定；未修改业务代码、运行时或构建配置。

## 一、结论与首发范围

当前已有可用的本地指纹浏览器和一个服务端原型，但还没有形成“用户注册 → 登录客户端 → 获得真实权益 → 使用环境 → 付款续费 → 到期处理 → 数据恢复与支持”的闭环。**现阶段不能直接对公众开放收费。**

首个可收费版本建议限定为 **Windows x64、单用户工作空间、本地运行环境、云端账号与订阅权益**。环境、Cookie 和平台登录状态仍保留在用户本机；云端只保存用户、订阅、设备与必要的环境元数据。团队共享、跨设备迁移完整浏览器数据、代理池托管、自动化接口和 AI 创作计费在首发后按真实需求逐项开放。这样能先卖一项确实交付的能力，同时控制一人开发与运维成本。

如果首发承诺“团队多人共享同一登录环境”或“换电脑立即恢复网站登录状态”，必须完成后文团队协同与敏感数据同步阶段，不能沿用上述首发时间估算。

## 二、现状核查：已有能力与实际缺口

| 范围 | 当前证据 | 判断 |
| --- | --- | --- |
| 指纹与本地环境 | `fingerprint-browser/main.js`、`browser-tabs.js`、`environment-repository.js` 和 `fp-kernel` 已有配置、独立会话、标签及本地持久化入口 | 有应用基础；正式售卖仍须以发行包实测能力和缺口报告为准，不能按旧评估中的“19 项 100%”宣传。 |
| 本地环境界面 | `renderer/saas-app.js` 的环境列表调用 `browserApi.listEnvironments()` 等本地接口 | 这部分接了真实本机数据，并非整页都是演示。 |
| SaaS 服务端 | `saas-server/src/server.js` 已有注册、登录、工作空间、环境、租约、成员、代理、账单查询和审计路由；`npm test` 本次 10 项通过 | 服务端**不是空白**，但仍是原型；测试通过只证明既有正常流程。 |
| 客户端与云端 | `main.js`、`preload.js` 未见登录、订阅校验及 `saas-server` 接入；界面明确提示云同步尚未接通 | 客户端仍可独立本地使用，云端权益无法控制实际使用。 |

需要纠正同目录《SaaS商业成品产研落地推进全景规划书.md》的两处过时判断：`saas-server` 已存在；“10 周完成团队版并上线”的前提与当前安全缺口、单人开发节奏不符。本计划以实际源码为排期基线，原文保留。

## 三、阻止公开收费的关键问题

1. **身份与权限安全。** 服务端可回退到内置签名密钥；首次初始化自动创建已知凭据的演示管理员；密码摘要使用 1,000 次 PBKDF2；邀请成员时使用固定临时密码。工作空间成员检查只验证“属于该空间”，环境增删、租约、代理列表和审计等路由没有统一执行角色及环境授权。必须在公开部署前移除这些路径，完成逐接口越权测试。密码存储的参数应按 [OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)重新选定并支持迁移；授权检查应放在服务端每次请求上，参照 [OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。
2. **数据与并发可靠性。** 当前服务端将全部租户数据写入单个 `saas-db.json`。环境更新的修订号由请求体计算，缺少数据库条件更新；租约和配额也没有跨进程事务保证。当前租约按环境 ID 全局查询，续期只检查租约 ID 和设备 ID，没有将路径环境、用户、工作空间与当前权限完整绑定。多实例、并发提交和崩溃恢复不能据此宣称可用。
3. **敏感信息。** 代理账号和密码直接进入服务端 JSON，并由代理列表返回；本地代理凭据也随配置保存。应先明确“不托管代理凭据”的首发边界，再做本机安全存储；若以后开放云代理池，需独立实现加密、密钥轮换、脱敏返回与权限控制。客户端已复制的数据无法靠服务端撤权远程抹除。
4. **商业闭环。** 服务端订阅由初始化数据生成，只有环境创建时检查数量；没有真实订单、支付确认、续费、退款、到期与超限状态机。客户端不登录也能创建和运行环境，不能靠隐藏按钮或前端限制实现授权。
5. **运行与交付。** 当前错误响应可能返回原始异常信息，跨域配置过宽；还缺生产环境密钥管理、限流、备份恢复演练、服务监控、正式发行包升级与回退验证。远程网页及 IPC 应继续满足 [Electron 安全清单](https://www.electronjs.org/docs/latest/tutorial/security)的隔离要求。

## 四、产品边界与技术方案

- **首发商品**：明确一个可交付套餐，例如单人按月使用一定数量的本地环境；价格、环境上限、试用期及退款规则由真实业务决策确定，现有界面中的 `¥99/299/899` 和“团队版有效”均不得充当正式报价。
- **云端权威数据**：用户、设备、订阅、订单、权益与必要的环境目录元数据。客户端可缓存短期授权以支持明确的离线宽限，但新设备登录、配额变化和续费结果以服务端为准。
- **本机权威数据**：指纹快照、Cookie、缓存、浏览器登录状态与代理凭据。首发不上传这些数据，界面直说备份责任和换机限制；提供本机备份、恢复与升级迁移验证。
- **服务端实现**：沿用现有 `saas-server` 业务入口，先替换单文件存储为单实例关系数据库及事务；初期不必引入微服务、Redis 集群、对象存储或 WebSocket。通过唯一约束、条件更新、事务和数据库时间实现配额及租约互斥，再以负载测试决定是否扩容。
- **客户端接入**：在主进程建立受控的云端 API 适配层；渲染层只获取必要状态，不直接持有长期密钥。登录、设备登记、权益刷新、退出及失效处理与本地环境启动流程贯通；无云端授权时遵守明确的离线规则。
- **功能展示**：每个导航页面标记为“真实接入、仅本地、尚未开放”之一。正式发行界面不保留演示成员、演示价格、虚构审计、虚构代理检测或假成功提示。保持现有 8 项导航静态保底、桌面缩放可见与左栏层级约束。

## 五、分阶段开发排期

以下按一名开发者连续投入估算，合计约 **10～14 个工作周**；支付机构开通、合规材料、域名与生产部署由实际外部条件决定，不计入固定工期。每阶段满足验收门槛后再进入下一阶段。

| 阶段 | 估时 | 开发任务 | 必须通过的验收 |
| --- | --- | --- | --- |
| 0. 冻结首发契约 | 0.5～1 周 | 确定单人套餐、环境计数、试用/到期/离线宽限规则；列出页面与接口真实/演示清单；固定数据模型和状态机 | 每个可见操作有真实数据来源或被关闭；形成一张“注册至续费”的时序与异常清单。 |
| 1. 服务端安全与持久化 | 2～3 周 | 移除默认管理员和内置密钥；升级密码摘要并迁移旧摘要；注册验证/找回/限流；会话撤销；以数据库迁移替换 JSON；所有资源统一授权；敏感字段脱敏；规范错误与审计 | 两个租户、四种角色、环境范围、撤权、越权 ID、并发更新、重启恢复全部通过；配置缺失时拒绝启动；备份能实际恢复。 |
| 2. 客户端登录与权益闭环 | 2～3 周 | 登录/退出、设备登记、权益缓存与过期处理；服务端核验创建和运行权限；本地环境映射云端 ID；断网、重连、冲突提示；去除首发页面的假数据与假操作 | 新用户真实注册后在安装版登录、创建、关闭、重启、恢复；超配额及过期无法新增；已打开环境可安全关闭；退出后敏感云端数据不可继续读取。 |
| 3. 订阅与付款 | 2～3 周 | 选定目标销售地区及支付渠道；订单、支付回调验签、重复回调幂等、支付失败/退款/续费/到期状态机；服务端统一授予权益；真实账单与用量 | 实际支付测试环境完成“下单→支付成功→权益生效→续费/退款/到期”；重复和乱序回调不重复发权益；订单与权益能对账。上线前再完成至少一笔小额真实支付和退款核验。 |
| 4. 发行与运维 | 2～3 周 | 生产配置、传输加密、数据库备份与恢复、监控告警、错误收集、隐私与服务说明；Windows 安装、升级、回退、运行时身份校验；客服诊断包脱敏 | 全新机器无源码安装；原有本地数据升级后不丢；服务停机/数据库恢复/客户端回退演练完成；下载包可核验版本与哈希。更新方式需与现有安装器兼容，不能直接套用其他打包体系的自动更新方案，参考 [Electron 更新文档](https://www.electronjs.org/docs/latest/tutorial/updates)。 |
| 5. 小范围付费试运行 | 1～2 周 | 邀请少量真实用户、收集安装/登录/付款/环境使用问题；处理阻断缺陷；核对支持工单和退款流程 | 用户在自己的 Windows 设备上独立完成首次购买与日常使用；无已知跨租户泄露、丢数据或支付错账；故障时可定位、恢复和联系支持。 |

### 首发后的团队阶段

当付费用户确有团队需求，再排期：可接受且可撤销的真实邀请、环境范围授权、成员席位计费、跨设备租约、审计留存与代理共享。完整浏览器数据同步另立专项：先定义 Cookie/缓存范围、加密与密钥恢复、冲突与损坏回滚，再做双设备实测。若只同步元数据，界面必须明确“换机后网站仍需重新登录”。

## 六、首个迭代的实施顺序

1. 先写首发套餐与离线权益规则，关闭会误导购买决策的演示价格、订阅和团队状态。
2. 为现有服务端增加“另一租户能否读取/改写环境、代理、租约和审计”的失败用例，确认安全缺口后修复。
3. 移除固定管理员、固定临时密码及密钥回退；把密码升级、限流、错误包装和会话撤销一起落地。
4. 迁移单文件存储与订阅数据，用数据库条件写入建立真实配额、修订冲突与租约规则。
5. 接通客户端登录和权益后，再开发支付；付款成功必须落到服务端权益，而非仅让页面显示“已购买”。

## 七、上线门槛与证据

- **安全**：身份、角色、租户和环境范围从 API 到本地敏感数据访问都可验证；无预置生产账户、默认密钥和明文云端代理密码。
- **业务**：注册、登录、购买、使用、续费、到期、退款均有真实状态与持久化记录；前端显示与服务端一致。
- **可靠性**：并发更新不覆盖，租约失效可接管，备份可恢复，升级与回退不损坏环境目录。
- **交付**：至少一轮干净 Windows 安装、真实发行包运行时校验、两台设备与两个租户的端到端验证；保留版本、测试结果和已知限制。
- **支持**：用户能看懂失败原因，诊断记录不包含 Cookie、代理密码和完整网页内容；高优先级故障有恢复步骤。

现有 `saas-server` 的 10 项测试本次执行通过，属于原型正常流程基线，不构成上述上线验收。当前工作树已有两处测试文件的未提交改动，本计划未触碰它们。
