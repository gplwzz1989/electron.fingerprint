- 默认启动器原来指向 2026-10-02 10:17 的 Testing，可执行文件及对象文件早于历史修复。
- 当前 Release 可执行文件为 2026-10-03 13:21，实际测试已在内核拦截该请求；它的 SHA-256 为 `426212649b947ac899fde396b3efa0108b5255733d5ff1d7bddca07561e0723e`。
- 现有 v3 便携包内仍为旧 Release，SHA-256 为 `c9f03f70b45d39c8cb0b2c1016f15a1323f5e7348938f30708a401e7fe3adc3f`。此前重新打包应用没有更新运行时，不能视为已发布内核修复。

## 已确认的问题

最初有两个独立问题：运行时与配置不匹配，以及代理执行环境的 Windows 权限限制。前者已通过明确提示的兼容处理解决默认配置启动，后者已在用户解除限制后通过实测确认。

### 运行时与配置不匹配

本地 `J:\awork\electron-fp-build\src\out\Testing\electron.exe` 修改时间为 2026-10-02 10:17:25。实际主进程报告 Chromium 138.0.7204.185、指纹内核 0.1.0，包含 `Session.setFingerprintConfig()` 接口。

该运行时加载项目默认配置时返回：

```text
Fingerprint 配置包含不支持字段: modules.runtimeInspector
```

当前项目的默认模板和配置存储会包含这个字段。因此，即使解决窗口启动权限问题，继续使用这份 Testing 运行时也会在启动配置时失败。

当前构建目录的源码已经包含 `runtimeInspector` 的解析逻辑，但这不能证明旧可执行文件已更新。需要使用完成构建后的匹配运行时重新验证。

这一配置错误发生在调用指纹配置接口时。管理界面初始化只读取配置文件，不会调用该接口，因此不能用这个字段错误解释最初管理界面没有出现。

### Windows 权限限制

官方 Electron 37.2.6 发布版与本地 Testing 运行时，均在创建最小窗口并加载页面时因进程通信管道访问被拒绝而崩溃。错误位置为 Chromium `mojo/public/cpp/platform/platform_channel.cc:89`，对应命名管道客户端的 `CreateFileW` 调用。

不调用 Electron 的独立 .NET 命名管道测试也复现：服务端创建成功，客户端连接返回权限不足异常。因此该故障不能归因于自定义指纹代码或 Release 优化。

网络数据目录的 DACL 修改同时被拒绝。关闭 Electron 自身的沙箱，不能解除代理执行环境对系统对象的限制。

最初新项目的启动日志还明确记录：无法创建 `C:\Users\Administrator\AppData\Roaming\指纹浏览器`，Windows 返回访问拒绝。项目的 `productName` 为“指纹浏览器”，对应这个默认应用数据目录；主程序随后也使用 `app.getPath('userData')` 保存配置。这个目录不在当前代理执行环境的可写范围内。显式指定可写数据目录后能够进入主进程，但窗口页面加载仍遇到前述管道权限限制。

原有指纹网站测试程序的应用名为 `fingerprint-live-test`，启动脚本显式使用 `--no-sandbox`，测试 Profile 没有 `modules.runtimeInspector` 字段。新项目默认启动没有该命令行参数，应用名与数据目录也不同。两者使用的是同一路径的 Testing 可执行文件，但启动条件并不相同。
