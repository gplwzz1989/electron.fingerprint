# 架构

FingerprintProfile 属于 Session 对应的 ElectronBrowserContext，不属于 BrowserWindow。

第一阶段链路：

```text
Session -> ElectronBrowserContext -> FingerprintContext -> Renderer
```

没有 Profile 时不添加任何 FP 配置，保持 Electron 原始行为。第一版配置在 Renderer 创建前确定，不支持热更新。

## 修改内核时的职责边界

本节是后续修改的设计约束，不表示现有代码已经完成全部解耦。构建仍必须遵守 [项目协作规则](../../AGENTS.md) 的缓存保护与增量预演要求。

| 所属层 | 负责内容 | 禁止扩散的职责 |
| --- | --- | --- |
| `fingerprint-browser` 应用层 | 页面、环境管理、配置选择、存储、产品业务 | 不将界面或产品规则写入 Chromium 补丁 |
| Electron 会话入口 | API 参数处理、配置校验、Session 所有权、启用与生命周期 | 不在 API 方法内持续堆叠各类指纹算法 |
| Electron 跨进程适配入口 | 将已校验配置映射到现有网络、渲染器及 Worker 入口 | 不把整个应用对象或浏览器进程指针交给消费方 |
| Chromium/Blink 能力模块 | 在所属层读取必要数据、执行能力、保留原行为回退 | 不依赖 Electron 实现，不访问业务存储或其他能力内部状态 |

运行时数据方向为：应用配置 → Electron 校验 → Session 配置快照 → 跨进程传输/原生覆盖接口 → 对应能力。这里的数据方向不代表可以建立反向 C++ 依赖；Chromium/Blink/V8 不得包含 Electron 头文件。

优先沿用现有入口，例如 User-Agent/Client Hints 的覆盖接口和网络偏好；只有现有接口确实无法实现能力时，才在对应 Chromium 层加入最小补丁。不要为同一能力同时维护互相竞争的多条配置路径。

## 当前代码入口与后续收敛位置

| 现有入口 | 当前职责 | 后续修改边界 |
| --- | --- | --- |
| `shell/browser/fingerprint/fingerprint_profile_parser.*` | 将输入配置校验并转换为内部配置 | 复用校验入口，按能力组织私有校验函数，不让每个调用方重复解析 |
| `shell/browser/fingerprint/fingerprint_context.*` | 保存会话配置与 Renderer 创建状态 | 保持 Session 所有权，不变成算法、持久化和传输的统一管理器 |
| `shell/browser/fingerprint/fingerprint_config.*` | 配置结构、序列化及现有覆盖辅助函数 | 保持数据契约稳定，避免继续往共享头文件添加不相关实现和依赖 |
| `shell/browser/api/electron_api_session.cc` | 配置 API 接入 | 保留参数接入与调用；新增复杂逻辑放到对应私有实现 |
| `shell/browser/electron_browser_client.cc` 等 | Renderer、网络及偏好适配 | 接入点保持简短，按能力调用适配函数，避免反复手写完整处理流程 |
| `patches/chromium/fp_*.patch` | Chromium 原生能力接入与实现 | 补丁按能力维护，挂接位置与算法实现分开，记录真实上游路径及依赖 |

目前多个 Chromium 补丁在各自 `.cc` 中解析 `fingerprint-config`；这是现状，不要求为遵守新规则立即批量改写。后续碰到同类逻辑时，先核验是否能在合法的共同依赖层复用已有读取入口，再在本次能力范围内收敛。不得把共享读取器放入 Electron 侧供 Blink 调用，也不得为了消除少量重复而建立跨层万能模块。

## 能力模块的最小组织方式

- 按硬件、屏幕、图形、噪声、语言/时区等实际能力组织私有实现；复用现有目录和命名，不规定每个开关都必须新建一个类或构建目标。
- 上游挂接点负责判断是否启用、调用所属能力入口、返回原有结果；字段解析、数值校验、噪声算法及平台策略放在相应私有实现中。
- 一个模块只暴露消费方确实需要的值，例如硬件并发度的可选覆盖值或图形噪声所需的种子与参数；不要把整个配置及所有模块状态作为通用依赖传递。
- 对可测试的算法优先使用明确输入和输出的普通函数；仅在确有状态及生命周期需求时使用对象。不要引入只有一个实现的接口、工厂、注册中心或回调总线。
- 共享规则只在实际存在多个消费方且所属层允许时复用；能力模块间不互相调用私有实现，协作由上层明确协调。
- 对既有内联或耦合逻辑的迁移采用局部、可验证的补丁，保留注释和公开入口；不得为了“组件化”批量移动未涉及的文件。

## 配置与生命周期隔离

- 配置在浏览器进程校验，传输边界及消费方仍保留类型、范围、长度和有效性检查。不能用“上游已校验”作为删除边界保护的理由。
- 复用现有配置协议和版本机制；增加字段时同时核验 Schema、解析器、序列化、传输和各消费方。现有顶层未知字段会被拒绝，不能假设新增字段天然兼容。
- 新字段必须明确缺省值、模块关闭行为和版本兼容策略；未设置配置、配置关闭或字段无有效覆盖值时，按既有契约保留原生行为。
- 模块开关和业务参数通过运行时数据表达；禁止为日常能力调整新增全局编译宏、改 GN 参数或修改内核版本常量。
- 同一配置快照在对应生命周期内尽量只解析一次；先确认配置在该范围内不会变化，再使用缓存。禁止在热点调用中反复解析整份 JSON。
- `FingerprintContext` 的 Session 隔离不能退化为进程级可变单例；Renderer/Worker 缓存必须核验进程复用、线程访问及配置传播，不能默认一个进程永远只属于一个会话。
- 不支持热更新的既有约束保持不变；涉及启动时配置或生命周期变更时，必须同时评估普通 Renderer、Worker、ServiceWorker、进程重启与会话复用路径。
- 各模块默认只读自己的快照数据；跨线程传递按现有线程约束管理对象所有权和生命周期，禁止保留指向短生命周期对象的裸指针。

## 限制编译依赖的连锁反应

代码边界、运行时状态隔离和编译隔离需要分别检查。把函数换到另一个文件夹，或仅新增 GN 目标，都不能证明重编范围已经缩小。

- 首选修改所属 `.cc`，避免无必要地改共享头文件。新增包含关系优先放在实现文件；类型允许时使用前置声明，禁止用不完整类型技巧破坏所有权或析构正确性。
- 头文件仅保留必要声明和稳定数据布局。频繁变更的实现、配置表及解析细节放在 `.cc`，避免增加大段内联/模板代码和对 V8、Blink 或平台 SDK 的传播依赖。
- 模块调用方只依赖窄接口，不为了单个字段包含完整业务配置。对于已经广泛使用的 `FingerprintConfig`，新增能力先考虑私有适配函数或局部所需数据；确需调整契约时必须核验全部依赖。
- 只有实际依赖边界需要时才新增 GN 私有目标。可选择与现有结构兼容的 `source_set` / `static_library`，收窄 `visibility` 和私有 `deps`；不得随意扩大 `public_deps` 或 `public_configs`。
- Blink `core`、`modules`、`content`、`base` 等层级仍遵守上游依赖方向；不能为了共享代码让底层反向依赖上层，也不能把产品专用代码随意塞进 `base`。
- 禁止通过忽略依赖检查、允许循环引用、扩大整个目标可见性来让构建通过。确需修改目标关系时先说明合法依赖方向，再做最小调整。
- 不切换 `is_component_build`，不创建新的动态库插件体系，不修改 LTO、优化或平台配置。组件化以现有构建参数和缓存为前提。
- 注意现有聚合编译、生成文件和链接方式：修改一个 `.cc` 也可能重编所属聚合单元；新增静态目标也可能仍需链接最终 Electron。必须以真实构建图和预演为准。

## 每次修改的执行与验收

修改前在任务说明中简要列出：所属能力、原生挂接点、需要修改的实现/头文件/协议、直接调用方、涉及 GN 目标及预计重编范围。对于共享接口，追踪源码引用和现有 GN 依赖，必要时在已有构建图上使用 `gn refs` / `gn desc` 查看影响；不得为了分析重新同步或创建空构建目录。

处理顺序：

1. 现有应用配置或公开接口能够实现时，优先在该层处理。
2. 需要原生实现时，先尝试修改对应能力的私有 `.cc`。
3. 需要复用时，在合法依赖层提供稳定窄接口，限定消费方和必要字段。
4. 最后才修改共享配置、公共头、IPC/Mojo/IDL 等生成协议或上游公共接口；说明局部方案为何不足，核验生产方、消费方及生成代码影响。
5. 比较修改前后的 Ninja 预演，确认实际失效文件与上述设计一致；超出预期时先调整实现位置、包含关系、接口或 GN 依赖，再进行预演。

| 修改类型 | 通常需要的验证与构建 | 必须核验的扩散风险 |
| --- | --- | --- |
| 应用页面、配置值或业务规则 | 复用现有运行时，验证应用行为及打包 | 是否错误触发原生编译 |
| 单个能力的私有 `.cc` 实现 | 定向行为验证、对应目标增量编译及必要链接 | 聚合编译单元、生成输入、无关任务失效 |
| 共享头或数据布局 | 全部实际消费方兼容验证及必要依赖重编 | 包含链、ABI、隐式耦合；不能承诺零传播 |
| 跨进程协议及生成接口 | 生产方与消费方、默认值及版本兼容验证 | 多进程路径、生成文件、目标依赖扩散 |
| 工具链、全局参数或上游版本 | 先评估现有缓存兼容性，不能直接构建 | 缓存不兼容时按项目规则停止，禁止全量回退 |

验收复用现有测试入口，覆盖本次能力开启、关闭、无配置、非法输入及相关 Session 隔离；涉及渲染/传输的变更补充对应 Renderer/Worker 路径，涉及线程的变更验证生命周期。关闭功能时其他模块及原生行为必须保持兼容。

同时报告实际重编与链接范围。解耦减少不必要传播，但公共头、协议和真实依赖变化仍可能需要必要重编；若无法保持既定缓存约束，停止并说明原因，不能把全量构建当成验收手段。
